# CONVENTIONS

Rules that outlive any tool in this repo. Tools get replaced; these do not. If code and this file disagree, one of them is wrong: fix it deliberately, never let it drift. Owner: Joe. Claude Code may propose edits here, but a schema change and its edit to this file land in the same commit.

## 1. Principles

**One home per quantity.** Anthropometric inputs, segment inertial data, joint centres and ROM live in the Freyja Anthropometric Reference sheet. Everything else is derived from them by code, or lives in exactly one authored file. A hand-typed copy of a value that exists elsewhere is a bug, even when it is currently correct.

**Authored or generated, never both.** Every file is one or the other. Generated files carry a banner (section 4), are never edited by hand, and are byte-reproducible from their inputs.

**Downstream reads the snapshot, not the sheet.** `pre_processor` is the only code that reads the live sheet. Checks, sim runs, the CAD bridge and reports read `params/snapshot.csv`. Any result is then reproducible from a commit.

**Provenance.** Every number entering the sheet or an authored file has a citation, or a script path that reproduces it. No circular validation: a model is never validated against the data it was built from.

**Staleness is a hash mismatch.** Every generated artifact records the hash of its inputs. A mismatch means stale, and tools say so instead of guessing.

**Checks are executable and can fail.** A claim of correctness is a named check. Every check has a mutation test proving it fails when the thing it guards is broken. Known deviations are recorded as explicit waivers (section 7), never as a quiet INFO.

**Determinism.** Build artifacts carry no timestamps or absolute paths. Time lives in the log, not in artifacts. Same inputs, byte-identical output. A run record is an event, not a build artifact: its `run_id` encodes the start time and nothing else in it is time-dependent, and every metric is deterministic given the same inputs and seed.

**No secrets in the repo.** Per-machine configuration lives in `local_config.json` (gitignored) or environment variables. The service-account key stays outside the working tree.

## 3. Identifiers

IDs are the join key across every artifact. Segments are lowercase letters, digits, underscore and hyphen, separated by dots. IDs are permanent: never reused, never deleted. A retired ID is marked superseded.

| Kind | Form | Example |
|---|---|---|
| Quantity key | existing `pre_processor` placeholder names; do not rename | `thigh_right_mass`, `hip_flexion` |
| Requirement | `req.<joint-or-subsystem>.<quantity>` | `req.ankle.df_min` |
| Decision | `adr-NNNN` | `adr-0012` |
| Part | `part.<assembly>.<name>` (revision is a field, not part of the ID) | `part.hip.ach` |
| Check | `check.<area>.<name>` | `check.mjcf.joint_signs` |
| Gate | `gate.<plan id, lowercase>` | `gate.g0`, `gate.g-h` |
| Run | `run.<YYYYMMDD>-<HHMM>-<scenario>` | `run.20261012-1430-walk_1p4` |
| Gait record | `gait.<YYYYMMDD>-<HHMM>-<spec>` | `gait.20261011-2232-walk_treadmill` |
| Design point | `dp-NNN` | `dp-003` |
| Open item | `oi-NNN` | `oi-014` |
| Roadmap node | `rm.<slug>`, slug of lowercase letters, digits and hyphens (no dots, no underscores); the filename stem equals the ID | `rm.elbow-actuator-selected` |
| Segment record | `seg.<pre_processor segment name>` | `seg.upper_arm` |
| Joint record | `jnt.<anatomical joint>` | `jnt.elbow` |
| Interface | `if.<slug>` | `if.hip-m2-thigh` |
| Load case | `lc.<slug>` | `lc.walk-1p4` |
| Harness run | `hn.<slug>` | `hn.leg-power` |
| Work item | `work.<slug>` | `work.thigh-cad` |

A thread **address** is `<source>#<JSON pointer, RFC 6901>` (empty pointer: the whole source), where the source is `snapshot`, a thread record id or a `req.` id, or the repo-relative path of a tracked JSON or YAML file; its hash is the sha256 of the canonical JSON of its value (sorted keys, no whitespace, non-ASCII kept) as 12 hex, with the banner keys `generated_by` and `inputs` excluded, and an address into one of the thread's own generated outputs resolves against a fresh in-memory build of everything but the work statuses, never the file on disk.

Roadmap node IDs obey the permanence rule: a retired node is never deleted; it carries `superseded_by`.

Filenames derive from the ID.

**CAD terms.** A **bound document** is a Fusion design that the bridge reads or writes; it has a **binding**, the authored `cad/bindings/<part id>.yaml` (`cad-binding/1`: part id, `revision`, the document's name and id, `side`, chord tolerance, `clearance_mm`, the parameter list). A Fusion document with no binding is invisible to the bridge. The **sidecar** is the generated `cad/sidecars/<part id>.json` (`cad-sidecar/1`), the one home of CAD-derived quantities (parameters, mass properties, export hashes, the envelope component, what the CAD state consumed). Every user parameter of a bound document is in exactly one of three **classes**, named by its prefix: **inherited** `in_` (owned by the repo, pushed one way from a thread address, never edited in Fusion), **design** `dv_` (owned by Fusion, `dv_<part short>_<quantity>`) and **derived** `dr_` (defined by an expression of other parameters, never set by the bridge). An unprefixed user parameter is an error. The **name rule** for an inherited parameter: `in_` plus the address with `snapshot#/` removed and every other `#`, `/`, `.` and `-` replaced by `_` (`snapshot#/upper_arm_right_length` is `in_upper_arm_right_length`; `req.elbow.flex_max#/value` is `in_req_elbow_flex_max_value`); two addresses mapping to one name is an error. Fusion names carry no unit suffix, because the expression carries the unit; the sidecar's keys carry units. The bridge writes a parameter only by setting its **expression with an explicit unit** (`"312.4 mm"`, `"62 deg"`, a bare number for unitless) and reads both the expression and the evaluated value; it never assigns `.value`. Fusion stores lengths in cm, angles in rad and inertia in kg cm^2 whatever the document's units; the one conversion module in `tools/cad/` is the only place those factors appear. **Snapshot and rollback**: before any write the bridge captures every user parameter's expression; after the write it recomputes and checks the timeline's health (every object's health state, the names of failed features); on failure, or when the task says so, it restores the captured expressions and verifies that they are equal and the timeline healthy. The capture lives in memory for the command, or in a file outside the repo when a command spans calls, and is never committed. Model parameters (sketch and feature dimensions) are not tracked; a dimension that matters must reference a user parameter (a modelling rule, not checked by the bridge).

**CAD frame.** CAD is modelled in the ISB segment frame of the **right** side, in millimetres: origin at the proximal joint centre, x anterior, y proximal (up in the neutral pose), z lateral (right); for the humerus, y runs from the elbow joint centre to the glenohumeral centre. The bridge converts to the owner's model body frame (x anterior, y left, z up, origin at the proximal joint centre, axes parallel to the world at q = 0) on pull, through `tools/envelope/registry.isb_to_segment` and never a second copy of that rotation. The left side is never modelled: a bilateral part is designed once on the right and carries `sides: [left, right]` in its thread record, and the left is its mirror. The bridge refuses `side: left`.

**Track terms.** Work runs on tracks, and a brief belongs to one. **Ariadne** is the digital thread: the pipeline from the sheet to the model, sims, load envelopes and later CAD and FEA (Stages 2, 3 and on). **Architecture** is the track for repo tooling, such as the roadmap. `CLAUDE.md` names one current brief per track.

**Roadmap terms.** A **node** is one file in `roadmap/nodes/`. Nodes form a strict tree by `parent` ("is part of"), with `blocked_by` edges laid over it that may cross branches. An **interior** node has children, carries no completion criterion, and takes its status from its children. A **leaf** is childless, sized to hours or a few days, and carries a `done_when` and an `estimate_days`. A **stub** is a childless placeholder not yet decomposed (`stub: true`), with neither. **`done_when`** is a leaf's completion criterion; "gate" stays reserved for blocking checks (section 7), and a `done_when` can reference a check. The **frontier** is every `ready` leaf plus every `expandable` stub, sorted by id. A leaf's `done_when` evaluates to `pass`, `fail`, `awaiting` or `unknown`. **Awaiting** means the evidence does not exist yet but could (the file is absent and its directory exists; the check is recorded as not run): normal for unfinished work, no warning. **Unknown** means the evidence cannot be read or expected (an unparseable record, a pointer that does not resolve, a missing directory, a check id that `docs/STATE.md` does not list) and draws a `criterion-unknown` warning. Neither counts as a pass. Status is derived on every evaluation and never stored in a node file; only a human decides `active`, `signed_off` and the criterion. A **tag** is free (no colon, never checked) or namespaced (`namespace:value`); a namespaced tag must name a namespace and value in `roadmap/tags.yaml` (an error naming the node and the tag, and a missing `tags.yaml` defines no namespaces), and a node carrying two values of one namespace draws a warning. Two namespaces exist, `region` and `phase`, and they are the roadmap's second and third axes beside the systems tree. A node may carry an optional **`short`** label (`roadmap-node/2`, at most 16 characters, no line breaks) for places too small for the title: map sector and node labels and breadcrumb segments before the last. The title stays in every tooltip and in the drawer. Files that say `roadmap-node/1` stay valid and may not carry `short`.

**Thread terms.** A **record** is one authored YAML file in `thread/records/`, the filename stem equal to the id, the kind given by the id prefix (segment, joint, part, interface, load case, harness run, work item); it carries `status` (`proposed`, `active`, `superseded`) and a `purpose`. A **binding** ties a segment record to its model body and a joint record to its hinges (and ROM keys); the snapshot keys of a segment follow from `pre_processor`'s naming, and topology, masses, lengths and ROM are read from the model and the snapshot, never restated in a record. A **relation** is stored once, on the record that owns it (`housed_in`, `acts_across`, `reacts_into`, `harness`, `between`, `carries_cut_of`, `path`, `of`, `consumes`); inverse relations are derived and never authored. An **address** is defined above. A **work item** is assisted or manual work (a CAD model, an FEA study, a fabricated part) whose output depends on the addresses it consumes. A **stamp** is an event record saying the work item's output was produced or checked against those addresses' values; the newest stamp by name is the baseline, and a stamp is **pinned** when it records `pinned: true`. **Work status** is derived on every build and never stored: `unstamped` (no stamp), `current` (every address in the baseline hashes as stamped), `stale` (one differs, baseline not pinned: rework), `drifted` (one differs, baseline pinned: a disposition for Joe), `unknown` (an address in the baseline no longer resolves) and `reverified` (reserved for margin-aware re-verification; never computed). The **rework queue** is every stale, drifted and unknown work item with the addresses that moved, stamped value against current. **Impact** of an address is the work items whose consumed addresses overlap it (one pointer a prefix of the other) and the generated outputs whose content depends on its source; the in-memory what-if applies an edit, rebuilds and reports what would change, writing nothing. A **budget** compares what a segment provides (its snapshot target) with what the parts housed in it claim; the mechanism is general and mass is the first budget. A part's `mass.kg` is the mass of one unit and `sides` gives one unit per side, so a bilateral part housed in a unilateral segment claims twice its `kg` there, and every budget row shows that arithmetic. A part's `reacts_into` must be the parent or the child segment of its `acts_across` joint.

## 4. Generated files

Every generated file starts with a banner naming its tool and inputs.

```
GENERATED by <tool> from <inputs> (snapshot sha256:<12 hex>). Do not edit; change the inputs and rebuild.
```

A generated file that does not depend on the snapshot (the roadmap files) carries `inputs sha256:<12 hex>`, the hash of its own inputs, in place of the snapshot hash, so a snapshot change does not rewrite it. Use the file type's comment syntax. JSON has no comments, so it carries top-level `generated_by` and `inputs` keys instead. Generated output is deterministic: sorted keys, LF line endings, no timestamps.

## 5. Parameter snapshot (`params/snapshot/1`)

`params/snapshot.csv` has columns `placeholder,value,sheet_source`, sorted by `placeholder`, values formatted by the same `fmt()` as `pre_processor`. It is rewritten on every successful build and only when its content changed. History is git history; read it with `git diff`.

`params/snapshot.meta.json` holds `schema` (`params/snapshot/1`), `snapshot_sha256`, `sheet_fingerprint` (the hash from `watch.sheet_fingerprint`), `template_sha256`, `model_sha256`, and `pre_processor_commit`. It must never contain the sheet ID, any credential, or an absolute path.

The banner in `sim/models/freyja.xml` carries the first 12 hex characters of `snapshot_sha256`.

If the sheet has a `targets` named range (`'BSIP Reference'!A1:B2`: label in column A with its unit in brackets, value in column B), its rows enter the snapshot as `target_mass` (kg) and `target_stature` (m), converted to SI, with the cell as `sheet_source`. They feed checks only; templates cannot use them. Without the range the keys are absent.

If the sheet has a `design` named range (key in column A, a number in B; the unit is part of the key; the keys and their meaning are in `docs/briefs/ariadne/stage2g-sheet-spec.md`, section 2), its sixteen rows enter the snapshot converted to SI under the snapshot names `stand_pelvis_tilt_deg` (degrees), `foot_heel_behind_ankle`, `foot_length_total`, `foot_ball_length`, `toe_hinge_ahead_ankle`, `toe_tip_ahead_ankle`, `foot_half_width`, `toe_height` (metres), `toe_mass_fraction`, `toe_com_fraction`, `toe_stiffness_nm_per_rad`, `toe_damping_nm_s_per_rad` and the four provenance inputs `ansur_female_stature`, `ansur_female_footlength`, `ansur_female_balloffootlength` and `ansur_female_malleolusheight` (metres; ANSUR II female means that nothing in the model reads and that a test compares with the public CSV), with the cell as `sheet_source`. Unlike `targets`, the template reads them, through `derive_keys`: the foot's box (from the heel to the toe hinge), the toe's box, hinge and inertial, and the foot body's inertial after the toe is split off the sheet's whole-foot row by conservation (`pre_processor.foot_split`). The whole-foot row stays in the snapshot as published; the derived values are not stored. A `design` range that is present must hold every key. A build without the range fails when the template asks for the foot geometry, and says so. The snapshot, its metadata and the model are installed together or not at all, and are written with LF line endings. `build_model()` writes the snapshot only when given a `snapshot_dir`; the command line and the watcher pass `params/` when building the default output.

## 6. Run records (`run-summary/1`)

Every sim run writes `sim/runs/<id minus "run.">/summary.json`. It is small and text-only, and is the thing Claude reads. Raw timeseries go in `raw.npz` beside it and stay gitignored; `summary.json` files are tracked, as are the generated `sim/runs/DIGEST.md` and `sim/runs/ENVELOPE.md`. The schema is `docs/schemas/run-summary-1.schema.json`, which carries the definition of every field and is validated on every write. It was amended in place before any record existed; after the first committed run, any change bumps the version.

```json
{
  "schema": "run-summary/1",
  "run_id": "run.20261012-1430-walk_1p4",
  "git_commit": "<sha>", "git_dirty": false, "diff_sha256": null,
  "snapshot_sha256": "<sha>", "model_sha256": "<sha>",
  "seed": 0,
  "env": {"mujoco": "3.10.0", "python": "3.11.9", "numpy": "2.4.6"},
  "scenario": {"name": "walk_1p4", "params": {}},
  "controller": {"name": "", "version": ""},
  "timestep_s": 0.002, "duration_s": 0.0,
  "support": "ground",
  "window": {"start_s": 0.0, "end_s": 0.0},
  "outcome": "completed",
  "joints": {
    "hip_fe_right": {
      "torque_source": "applied",
      "torque_peak_nm": 0.0, "torque_rms_nm": 0.0,
      "speed_peak_rad_s": 0.0, "power_peak_w": 0.0,
      "rom_used_deg": [0.0, 0.0], "rom_limit_deg": [0.0, 0.0],
      "limit_hit_fraction": 0.0
    }
  },
  "contacts": {"foot_right": {"normal_force_peak_n": 0.0, "friction_ratio_peak": 0.0}},
  "balance": {"support_margin_min_m": 0.0},
  "checks": {"passed": [], "failed": [], "waived": []}
}
```

`outcome` is `completed`, `fell` or `diverged`. `support` is `ground`, `gantry` or `ground_wrench`. A `ground_wrench` record is a static solve (`drive: static_equilibrium`, `sim/scripts/statics.py`): contacts are disabled for the call and the ground reaction is supplied explicitly as generalized forces through the foot Jacobians, so nothing goes through the contact solver; its window has zero width, its duration is zero, each joint's `torque_peak_nm` equals its `torque_rms_nm` and its speeds and powers are zero, and a pose that cannot be held (CoP outside the support polygon, a joint outside its range) is recorded as `fell` with the reasons in the optional `findings` list. `torque_source` is `applied` (ideal joint torque on `qfrc_applied` in forward dynamics, ground mode) or `inverse_dynamics` (`mj_inverse` with prescribed `qacc`, gantry mode only: with floor contacts the inverse contact force comes from the soft-constraint model, so the root rows do not close). `diff_sha256` hashes `git diff HEAD` and is null when the tracked tree is clean. Scenario files may carry `envelope: false` (default true): a verification-only run, listed in `sim/runs/ENVELOPE.md` as excluded with that reason and never driving a row. Optional record keys: `skipped` (joint to reason, e.g. `unlimited`) and `diagnostics` (scenario-specific named numbers). Joint torque is about the model's own hinge axes (the decoupled hip architecture); it is not actuator torque for a coupled-hip variant. Units are SI except angles in degrees, and are named in the key suffix.

Stamps (`thread-stamp/1`, section 8) are event records like a run record: the stamp id encodes the time and nothing else in a stamp is time-dependent.

Gait records (`fy gait <spec>`) write `sim/gait/<id minus "gait.">/gait.json` (`gait-summary/1`, schema `docs/schemas/gait-summary-1.schema.json`) and generated markdown, every file under 400 lines: a shared `GAIT.md` (header, assumptions, subjects, the band table of every speed, the sensitivity runs) and one `GAIT-<speed>.md` per speed (`0.5` is `0p5`) holding that speed's tables. A record is stamped like a run (commit, `git_dirty`, `diff_sha256`, snapshot, model, spec and dataset-manifest hashes, environment) and keys every result by speed and then by trunk mode. It lists the assumptions it rests on, and the Camargo et al. 2021 attribution (CC BY 4.0) is in its header. Loads are computed three ways: B (Freyja's own dynamics), A (the measured ground force and CoP scaled) and H (Freyja's own total force at the measured CoP). The method constraint above is extended for these frames: `mj_inverse` with contacts and joint limits disabled and the ground wrenches supplied explicitly is permitted for dynamic frames (non-zero `qvel` and `qacc`); the contact solver is never used for loads. `sim/benchmarks/walk_reference.json` pins the agreement of the methods that meet the envelope band (correlation at least 0.9 and RMS at most 15% of the dataset's peak-to-peak for the sagittal hip, knee and ankle) to a snapshot hash, and `check.sim.walk_reference` (advisory) reproduces it while the snapshot and model are unchanged and reports for information, never failing, once they change. `sim/runs/ENVELOPE.md` takes its gait rows from the tracked extract below, never from a `gait.json`, with the 95th percentile across subject-strides as the statistic and the maximum beside it, and lists the scenario classes it does and does not cover.

The gait extract (`sim/benchmarks/gait_extract.json`, `gait-extract/1`, schema `docs/schemas/gait-extract-1.schema.json`) is generated by `fy gait <spec> --write-extract` (or `--extract-only`, from the newest existing record) and tracked, so that `fy runs envelope` reproduces `ENVELOPE.md` byte for byte from a clean clone. It is stamped like `walk_reference.json` (commit, `git_dirty`, `diff_sha256`, snapshot, model, spec and dataset-manifest hashes, the source `gait_id`), carries the Camargo et al. 2021 attribution, and holds exactly what the envelope's gait section prints: per speed and trunk mode the stride counts, band verdicts, pooled agreement and, per leg joint and method, the 95th percentile and maximum of peak torque, speed, positive power and regeneration under each exclusion set the record has; the joints above the pelvis; the lumbosacral lateral and axial rows for `rigid`, `counter_rotate` and `first_harmonic` (the T3c.2 median gain and lag, with the quartile corners as the spread), computed over every subject-stride by the code of `gait_diag.py harmonic`; for `A_filtered`'s sagittal rows the dataset-direct scaled peak torque, the OLS slope against the dataset per kg and the peak ratio; and the dataset's hip extension from the vertical and relative to the pelvis. It is deterministic and carries no threshold or flag.

Posture sweeps (`fy sweep <spec>`) write `sim/sweeps/<id minus "sweep.">/sweep.json` (`sweep-summary/1`, schema `docs/schemas/sweep-summary-1.schema.json`) and a generated `SWEEP.md`. A sweep record is stamped like a run (commit, `git_dirty`, `diff_sha256`, snapshot and model hashes, environment, the spec) and holds every grid point, but creates no run directory per point. It is deterministic (timing is printed, not recorded), `SWEEP.md` is under 400 lines, a grid is limited to 2000 points, and a minimum over it is a property of the model, not a recommended posture.

## 7. Checks

Checks live in `checks/`, run under pytest (`pytest.ini` collects `tests/` and `checks/`; the old unittest suites now live in `tests/`), and tag themselves with their ID and tier:

```python
@pytest.mark.check("check.mjcf.mirror", tier="gate")
```

A **gate** check blocks installation of a new `freyja.xml`: `build_model()` runs the checks on the temporary XML through its `post_checks` hook (`pre_processor.py` and `watch.py` both pass it), and on a gate failure parks the new XML as `freyja_FAILED.xml`, leaves the last good model, snapshot and metadata in place, and prints the failing check IDs. `--no-checks` skips the hook, as does a scratch build with `--output`. Advisory results are printed and written to `checks/last_run.json` (gitignored). An **advisory** check reports and never blocks. Checks run offline, deterministically, and in seconds. Every tolerance is a named constant with its unit and its reason in a comment. Every check has a mutation test: a deliberately broken copy of the model on which the check must fail.

Known deviations are recorded in `checks/waivers.yaml`. A waived check still runs and reports as WAIVED. A waiver on a check that now passes produces a warning, as does one that names an unknown check or is past its `review_by` date. A waiver takes effect only with `confirmed: true`; Claude may propose one with `confirmed: false`, and Joe confirms it.

The machinery is `checks/checklib.py` (registry, context, waivers, `run_checks`), shared by pytest, the build gate and `fy check`; the checks are in `checks/mjcf_checks.py` (the model), `checks/sim_checks.py` (run records) and `checks/thread_checks.py` (the thread records; run by `fy check` and pytest, not by the build gate). A check returns one or more results, and a result may carry its own ID (`check.mjcf.mass_closure.target` is the advisory half of `check.mjcf.mass_closure`). A check whose ID is unknown to the registry cannot be waived. `checks/joint_polarity.yaml` carries `status: DRAFT` until Joe approves it; while it is DRAFT, `check.mjcf.joint_signs` reports as advisory.

```yaml
- check: check.mjcf.com_pct_stature
  reason: Whole-body CoM at 55.26% of stature, ~0.1% below the Virmavirta & Isolehto band
  source: docs/memos/memo1b.md          # Validations section
  recorded: YYYY-MM-DD
  review_by: YYYY-MM-DD
  confirmed: true                       # false = proposed, has no effect
```

**Notebook** (`notebook/YYYY-MM-DD-slug.md`) carries front matter `origin: me | source | claude`, plus `source:` for anything read. Notes of `claude` origin record decisions and open questions, not narrative.

**Thread record** (`thread/records/<id>.yaml`, `thread-record/1`, schema `docs/schemas/thread-record-1.schema.json`). Every record has `schema`, `id`, `kind`, `status`, `purpose`, optionally `notes` and (when superseded) `superseded_by`. One short example per kind (bilateral records carry `sides: [left, right]`, checked against `pre_processor.BILATERAL`):

```yaml
# seg.thigh          kind: segment      body: thigh                                   # binds thigh_right, thigh_left; keys thigh_<side>_<column>
#                                       also_bodies: [toe]  (optional, seg.foot)      # further bodies the segment owns, named like body (the foot's toe: toe_right, toe_left)
# jnt.hip            kind: joint        hinges: [hip_fe, hip_aa, hip_ier]             # binds hip_fe_right, ...
#                                       rom_keys: [hip_flexion, hip_extension, ...]

#                                       mass: {kg: 1.2, source: <citation>, reserved: false}   # kg is the mass of one unit; sides gives one unit per side. harness: [hn.leg-power], category, catalog, sides
#                                       second form of mass (a CAD part): mass: {address: cad/sidecars/part.arm.upper_member.json#/mass_properties/mass_kg, source: <text>}   # resolves at build to kg of one unit; no typed copy
# if.hip-m2-thigh    kind: interface    between: [part.hip.m2, seg.thigh]             # carries_cut_of: jnt.hip; mechanical, electrical, thermal: {status: open|defined, notes}

# work.thigh-cad     kind: work_item    of: seg.thigh; mode: assisted|manual; consumes: [snapshot#/thigh_right_mass, part.hip.m2#/housed_in]; output: <path>
```

A decision's link to a record lives in the decision's `links:` front matter, never on the record.

**Thread stamp** (`thread/stamps/<work id>/<YYYYMMDD-HHMM>.json`, `thread-stamp/1`, schema `docs/schemas/thread-stamp-1.schema.json`): `schema`, `work`, `stamp` (equal to the filename stem), `consumes` (a list of `{address, hash, value}`; `value` is the address's value when its canonical JSON is at most 2 KB, otherwise null), `note`, `pinned`, `by`. Written only by `fy thread stamp`, never edited.

**CAD binding** (`cad/bindings/<part id>.yaml`, `cad-binding/1`, schema `docs/schemas/cad-binding-1.schema.json`). `address_unit` is the unit of the value at the address (the snapshot holds metres), `unit` the Fusion unit of the expression:

```yaml
schema: cad-binding/1
part: part.arm.upper_member
revision: p1
document: {name: freyja-upper-arm-member, id: <Fusion data file id>}

chord_tolerance_mm: 0.05    # default

  - {name: in_upper_arm_right_length, class: in, address: "snapshot#/upper_arm_right_length", address_unit: m, unit: mm}
  - {name: dv_uam_od, class: dv, unit: mm}
  - {name: dv_uam_wall, class: dv, unit: mm}
  - {name: dr_uam_id, class: dr, unit: mm}
```

**CAD sidecar** (`cad/sidecars/<part id>.json`, `cad-sidecar/1`, schema `docs/schemas/cad-sidecar-1.schema.json`), generated by `fy cad pull`, banner keys `generated_by` and `inputs`, no timestamps, abridged here:

```json
{"schema": "cad-sidecar/1", "generated_by": "tools/cad pull", "inputs": "sha256:<12 hex>",
 "identity": {"part": "part.arm.upper_member", "revision": "p1", "side": "right", "binding_sha256": "<12 hex>"},
 "document": {"name": "...", "id": "...", "version": 7, "unsaved_changes": false},
 "parameters": [{"name": "in_upper_arm_right_length", "class": "in", "expression": "255.2347 mm", "value": 255.2347, "unit": "mm",
                 "address": "snapshot#/upper_arm_right_length", "address_hash": "<12 hex>"}],
 "drift": [], "timeline": {"healthy": true, "failed_features": []},
 "mass_properties": {"material": {"name": "...", "density_kg_m3": 2700.0}, "mass_kg": 0.0, "com_mm": [0, 0, 0],
                     "inertia_kgmm2": {"ixx": 0, "iyy": 0, "izz": 0, "ixy": 0, "ixz": 0, "iyz": 0}, "accuracy": "..."},
 "exports": {"stl": {"path": "...", "sha256": "<64 hex>", "chord_tolerance_mm": 0.05, "normal_deviation_deg": 9.36, "chord_bound_mm": 0.05, "chord_guarantee": true, "triangles": 0},
             "step": {"path": "...", "sha256": "<64 hex>"}},
 "component": {"id": "part.arm.upper_member", "revision": "p1", "name": "...", "status": "designed", "clearance_mm": 2.0, "mass_kg": 0.0,
               "sha256": "<64 hex>", "parameter_inputs": "<12 hex>", "primitive": {}, "mesh": "cad/exports/part.arm.upper_member.stl"},
 "consumes": [{"address": "snapshot#/upper_arm_right_length", "hash": "<12 hex>"}]}
```

Fusion's STL export follows its normal deviation alone and ignores its surface-deviation setting, so the bridge turns the binding's chord tolerance into a normal deviation from the largest analytic arc radius (clamped to 2 to 15 degrees) and records what that achieves: `chord_bound_mm`, the worst-case chord error of the analytic arcs, and `chord_guarantee`, false when any face is neither planar nor an analytic surface (free-form), in which case the bound says nothing about those faces. A tessellated convex surface lies inside the true one, so a clearance measured to the mesh is optimistic by up to the bound.

**Saving.** `fy cad push` records whether the document had unsaved changes before it writes. If it was clean and the recompute is healthy and changed something, it saves a new version whose description names the pushed addresses, and the next pull records that version. If it was not clean, it sets the parameters and does not save. The sidecar's `document.unsaved_changes` is true when the document had unsaved changes at pull; the pulled state is then not that of `version`, and `fy cad stamp` refuses until the document is saved and pulled again. The sidecar's `component` entry also feeds `data/envelope/components/cad/<segment>.yaml`, generated beside the authored registry.

A part's `mass` has two forms: the typed `{kg, source, reserved}` and the address form `{address, source}`, which resolves at build to the mass of one unit in kg and is how a CAD part's budget row reads the sidecar. A record carries exactly one of the two.

## 9. Rules for Claude Code

1. Read this file first. Run `fy test` (or, until `fy` exists, the baseline commands in the current brief) before and after every change.
2. Write the test or check first, watch it fail, then implement.
3. Never hand-edit a generated file. Never touch `local_config.json`, credentials, or the sheet.
4. Do not change what `pre_processor` reads from the sheet, or the meaning of any placeholder, without asking.
5. A check that fails on the current model is a finding, not a bug to fix silently. Report the measured number and stop.
6. No new dependency without asking. No `eval`. No network access in tests.
7. One commit per task, with the evidence (test output) in the message.
8. Roadmap nodes: Code never sets `signed_off`. Code never edits the `done_when` of a node that is `active` or that the current brief has Code working on. Code creates or edits nodes only when a brief says so. `done_when` thresholds are authored by Joe or in a brief before the work starts.
9. Any defect you observe in a path Joe uses (the CLI, the viewer, a hook, a workflow) is a finding and goes in the memo, even when it lies outside the task you are on. Fixing only the test that exposed it, and leaving the path broken, is not reporting it.
10. When tasks are coupled (one change cannot be built or tested without the other), say so before building and propose one combined commit. Never reconstruct per-task commits after the fact.
11. Thread records: Claude Code creates them only as `proposed` and never sets `active` (the seeded segments and joints of the Stage 3a brief, T7, are the one exception, and that brief says so). It never stamps a manual work item unless the prompt tells it to.

12. Fusion (Stage 3b). Fusion is Joe's live application: Claude Code opens or writes only the scratch fixture documents it created (names starting `freyja-bridge-fixture`) and the bound document Joe names for a task, through its parameters only. It writes parameters only as expressions with explicit units, never as values. It never edits features in a bound document and creates geometry only in scratch fixture documents. It sets a `dv_` parameter only inside a task that says so, through snapshot and rollback. It saves only through `fy cad push`, only a document with a binding (the scratch fixture has one) that had no unsaved changes before the push, and only after a healthy recompute (section 8, Saving); it never saves any other document, never saves a document for the first time, and never saves one that had unsaved changes.
