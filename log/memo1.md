The focus of this two week sprint is writing a simplistic mujoco model for freyja on which to build. Eventually this model will be used to size actuators, verify coupled kinematics, and model diverse fall cases among other applications. We have written the MJCF file with ten rigid body segments to serve as our base. Joints have been built in with defined RoM's (anatomical ceiling values), for multi-dof joints such as the hip we are using a serial gimbal config with multiple hinge joints. The order of the joints defined in the MJCF file reflects intended construction (if applicable) in the real world, eg ankle_pdflex before ankle_ie means that inversion/eversion is subordinate to plantar/dorsiflexion. 

The hip architecture is the non-coupled orientation with axes "0 -1 0", "1 0 0", and "0 0 1" (right hip) in mjc coordinated. The coupled config will follow as a variant. The decision to prioritize non-coupled first arises from the goal of obtaining a working model as quickly as possible. Both architectures will eventually be constructed so no time is wasted by building the non-coupled, and we expect time to be saved by learning mujoco on a simpler scope and then exanding to the target coupled configuration.

 Segment length, mass, COM, BSIP data, and RoM parameters were sourced from directly from the ground truth anthropometric reference sheet. A python program (see scripts/pre_processor.py) is being constructed to pull values directly from the cloud and build the MJCF with them so that changes to the ground truth parametrically propagate into the model without the need for a human to copy them by hand. The program will also check the entered values and throw errors when they do not meet the correct format, or when they are non-physical, to provide easier an diagnostic. A CSV of the values will also be pushed to an archive for debugging and history purposes. The current state of the program is still design and early implementation. The sheet has been linked to the program via the google api and a service account, values can reliably be pulled. We are currently experimenting with pulling rows and storing that data in a dictionary in preparation for pushing it to the MJCF. The next steps on the program are to pull the RoM and position/offset data, import a template file with parameters in place and use string.replace() to convert those parameters into values. Perform checks and implement the CSV code, and finally make the program robust by eliminating its reliance on hardcoded row and column numbers. This program will be eminently useful and is necessary, but it has consumed more learning and implementation time than the entirety of the MJCF model so far and it is not close to finished. 
 
Current status of the model: visually it looks relatively accurate, checks will need to be performed to ensure that it inertial pos's are correct. The first of those is the scripts/stature_check.py, it is currently returning a number that is off by about 50%. We credit that to manual transcription and edits to the reference sheet that were only partially propagated. Rather than manually fixing them we have elected to get the pre_processor online and then simply pull the correct values directly from the sheet. Joints have been visually tested in the simulator viewer to ensure that the axis orientations produce the correct ISB defined rotation via the right hand rule (eg positive rotation of the hip_fe axis produces flexion, positive rotation of the hip_aa axis produces adduction, etc).

The next steps are getting the pre_processor online, pulling the data to remove any manual transcription errors, and then performing checks such as stature to verify the model is performing as desired before continuing to build on it (controllers, the coupled version, etc).
